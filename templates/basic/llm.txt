# Basic starter installation instructions for an AI assistant

Set up the Vite/React web app, PostgreSQL, Better Auth, and the API. Follow the user's chosen project name and directory. Do not run generators in the source template repository; work inside the newly created project. Ask before overwriting an existing project, environment file, database, or migration. Never print or commit secrets. Follow the steps below in order. Treat each step as a prerequisite for the next: if a command fails, a required file is missing, or access is blocked, stop dependent commands and tell the user what they must do before you can continue. Do not work around a safety restriction with another tool or command. In particular, never run `pnpm db:generate` or `pnpm db:migrate` just to see if they work when schema generation has not succeeded.

1. Check prerequisites: Node.js 24+, pnpm 12, and Docker Compose with a running Docker engine. If the project does not yet exist, create it with:

   pnpm dlx create-turbo@latest <project-name> --example https://github.com/madflow/projectx/tree/main/templates/basic --package-manager pnpm

   `--package-manager pnpm` avoids an interactive selection prompt in non-interactive shells. Change into the new project directory and run `pnpm pkg set name=<project-name>` to update the root `package.json` name: `create-turbo` leaves it as `my-turborepo`. Use the same name the user chose for the new directory. `create-turbo` copies the example but does not run its generators. If a project was already created, use that project instead of creating another one; check its root package name and rename it if needed.

2. Install the starter dependencies if create-turbo did not already do so, then add the optional database and auth/API workspaces in order:

   pnpm install
   pnpm turbo gen database
   pnpm turbo gen auth
   pnpm install

   The database generator creates `packages/db`, `compose.yaml`, and `.env.example`. The auth generator adds `packages/auth`, `packages/api`, `apps/api`, the login UI, and the auth variables in `.env.example`. Neither generator needs a yes/no confirmation. Do not rerun them over workspaces that already exist. If starting from an existing project, confirm both generators have already run before proceeding; if auth has not been added, do not treat this as a database-only install. Do not run `pnpm check` yet: auth imports `@repo/db/schema/auth`, which does not exist until step 4 generates it.

3. Set up the local environment only after both generators. Review the non-secret `.env.example` defaults first: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `DATABASE_URL`, `BETTER_AUTH_URL` (`http://localhost:3000`), and `WEB_ORIGIN` (`http://localhost:5173`). The example database password is for local development only; if these defaults do not suit the project, ask the user to configure their environment instead of proceeding with them. If the defaults are suitable, run:

   pnpm env:init

   On a fresh project, this command copies `.env.example` to `.env` and fills `BETTER_AUTH_SECRET` with a cryptographically random value without printing it. It refuses to overwrite an existing `.env`. A successful command is sufficient to continue with the reviewed example defaults; do not read back `.env` just to confirm the secret. If `.env` already exists, do not rerun initialization or overwrite it; ask the user to verify its values and secret (at least 32 random characters) without sharing the secret. If `env:init` fails or access to `.env` is explicitly blocked, stop. Do not try another tool or script to inspect or modify it; ask the user to configure or verify it and wait for confirmation. Never print or commit `.env`. Do not start the API with unverified settings.

4. First generate the Drizzle auth schema from the Better Auth configuration:

   pnpm auth:generate-schema

   Confirm the command succeeded and `packages/db/src/schema/auth.ts` exists. If it cannot be generated, stop here; an empty `packages/db/src/schema/` has no tables to migrate. Only then create the SQL migration:

   pnpm db:generate

   Do not run `pnpm db:migrate` after a failed `db:generate`. `packages/auth/src/schema.config.ts` is the source of truth for auth options and schema-affecting plugins. Better Auth 1.7.6 generates `packages/db/src/schema/auth.ts` with plural table names, UUID IDs, PostgreSQL `gen_random_uuid()` defaults, and relations for joins. Generate this schema before running `pnpm check`; it needs the root `.env` from step 3, but not a running database. `pnpm db:generate` creates SQL migrations under `packages/db/drizzle/` from all `packages/db/src/schema/*.ts` files. Review generated migrations before applying them, especially if this is not a fresh database. Do not hand-edit the generated auth schema; regeneration replaces it.

5. Start PostgreSQL, wait for it to be healthy, and apply migrations:

   docker compose up -d
   pnpm db:migrate

   Only run `pnpm db:migrate` after a successful `pnpm db:generate`, review of the generated migration, and confirmation that PostgreSQL is healthy and `DATABASE_URL` points to it. If any of these are blocked, stop and report the blocker instead of attempting the migration. Do not delete volumes or run `docker compose down -v` against data that might need to be kept. Better Auth's `migrate` command is not used with this Drizzle adapter; `pnpm db:migrate` applies the SQL generated by Drizzle.

6. Run `pnpm check`, then `pnpm dev`. Open `http://localhost:5173` for the web app. The API runs at `http://localhost:3000`; check `/api/v1/health` and `/api/v1/docs`. Report what passed, what remains unverified, and any prerequisite or permission that blocked setup.

When auth plugins or other auth schema options change later, rerun `pnpm auth:generate-schema`, `pnpm db:generate`, and `pnpm db:migrate` in that order. For other app tables, add separate files under `packages/db/src/schema/`. See `README.md` for development details and PostgreSQL upgrade precautions.
